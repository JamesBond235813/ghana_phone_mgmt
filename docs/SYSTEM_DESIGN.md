# 深圳—加纳二手手机流转管理系统

## 1. 文档目的

本文是系统开发的业务与技术基线，覆盖深圳采购、托盘整理、装箱发运、加纳接收验收、管理处库存、门店库存、门店调拨、批发/零售销售、销售退回、维修、盘点和全程追溯。

系统不开发独立 Android/iOS 客户端。工作人员使用手机浏览器访问 Web 系统，并可将系统安装到手机桌面，以 PWA 方式获得接近 App 的启动和操作体验。

## 2. 总体设计结论

系统采用“IMEI 是资产主体，托盘和箱子是可重组容器，业务单据是操作入口，库存流水是审计依据”的模型。

核心关系：

```text
箱子（可选） → 托盘（可选） → 手机（IMEI）
```

- 托盘不设置槽位编号，只记录手机是否属于某托盘。
- 箱子不要求固定托盘数或固定手机数。
- 一个托盘中的手机数量可以不同；一个箱子中的托盘数量和手机数量也可以不同。
- 箱子和托盘可以拆开、复用、重新组合。
- 业务操作可以按单台手机、多台手机、托盘或箱子发起。
- 容器级操作提交时必须展开为具体 IMEI 快照，确保每台手机可追踪。
- 托盘和箱子的编号只表示标准容器本身，不表示容量、槽位或固定装载清单；同一批容器之间的手机数、托盘数都可以不同。
- “按托盘/按箱子操作”表示以容器作为扫描和选择入口；真正发生库存变化的对象始终是展开后的 IMEI 明细。
- 当前库存以手机 IMEI 为准，不以箱数或托盘数推算。

## 3. 业务对象

### 3.1 手机

手机以 IMEI 为唯一业务识别码。双卡手机可同时保存 IMEI1、IMEI2，但默认以 IMEI1 作为主查询码，并对两个 IMEI 建立唯一约束。

手机档案建议包括：品牌、型号、容量、颜色、成色、电池健康度、锁机状态、外观检测结果、采购价、当前状态、当前组织、当前地点、当前托盘、当前箱子和相关照片。

### 3.2 托盘

托盘是有编号的标准容器，但不管理槽位。托盘可以为空、包含任意数量手机，也可以暂时不装入箱子。

### 3.3 箱子

箱子是有编号的标准容器。按照当前现场包装方式，箱子通过托盘承载手机；箱内可以包含任意数量托盘，箱内托盘数量和手机总数不设固定值。箱子可在不同阶段拆封、清空、重新装货和复用；系统不因箱号复用而覆盖历史关系。

### 3.4 组织和地点

组织层级建议为：公司 → 国家 → 管理处/深圳网点/门店 → 仓库或区域。地点还可以有货架、散件区、待验收区、维修区等业务区域，但不强制要求手机必须在箱或托盘内。

## 4. 手机状态与允许流转

主要状态：

```text
待入库
深圳库存
待装托盘
已装托盘
已装箱待发运
运输中
加纳待验收
加纳管理处库存
门店库存
调拨中
销售待确认
已售出
销售退回待检测
待送修
维修中
维修完成待验收
可再次销售
冻结待核查
报损/遗失
```

状态转换必须由业务单据触发，禁止直接编辑库存状态。典型链路：

```text
采购入库 → 深圳库存
深圳发运 → 运输中
加纳接收 → 加纳待验收
验收通过 → 加纳管理处库存
仓库出库 → 调拨中/门店待收货
门店收货 → 门店库存
销售确认 → 已售出
销售退回 → 销售退回待检测
送修 → 维修中
维修完成 → 维修完成待验收/可再次销售
```

系统应拒绝不合逻辑的跳转，例如已售出手机再次普通出库、非当前库存手机被重复出库、未验收手机发给门店、维修中手机销售等。

## 5. 全流程设计

### 5.1 深圳采购入库

创建采购批次，连续扫描手机标签条形码。扫描成功后显示机型和 IMEI 后四位，并用声音、震动和颜色提示结果。服务端校验 IMEI 长度、校验位、重复性和当前状态。

采购人员可补录供应商、价格、成色、电池健康度和外观照片。条码扫描失败时允许手工输入或批量导入，但手工输入必须二次确认。

### 5.2 装托盘

扫描或创建托盘码，再连续扫描手机。系统只建立“手机—托盘”关系，不记录槽位。提交时显示托盘内手机总数和清单。

已属于其他托盘的手机必须提示并禁止重复加入，除非先执行转移/拆托盘操作。

### 5.3 装箱封装

扫描或创建箱码，再扫描托盘码。系统建立“托盘—箱子”关系，并自动汇总箱内手机数量。多个托盘数量不必相同，系统只显示实际数量。

封箱确认记录封条号、照片、封箱人、时间、箱内托盘数和手机数。封箱后若要拆箱，必须通过拆箱单处理，不能直接修改关系。

### 5.4 深圳发运

创建发运单并加入箱子，必要时也支持加入托盘或散件手机。发运单生成装运快照，记录物流单号、承运商、运输批次、起运地、目的地、发运人和附件。

发运确认后，所有涉及手机进入运输中；系统保存发运单、箱、托盘和 IMEI 的对应关系。

### 5.5 加纳接收、拆箱、验收和重新整理

加纳管理处先扫描发运单或箱码，确认箱子已到达。随后执行拆箱，结束旧的箱—托盘和手机—托盘当前关系，但保留历史。

逐台验收手机时，系统显示理论资料并记录实际结果：正常、缺失、多收、IMEI 不符、运输损坏或待复核。验收通过的手机可立即加入新托盘、原托盘，或暂存于散件区；托盘可继续加入新箱、原箱，或暂不装箱。

只有验收通过的手机进入加纳管理处可用库存。异常手机进入冻结待核查，不得直接配送门店。

### 5.6 管理处向门店出库

支持扫描箱子、托盘或手机。箱级出库自动展开箱内当前全部托盘和手机；托盘级出库展开该托盘当前全部手机；手机级出库选择一台或多台 IMEI。若现场只移动容器中的一部分，必须改用实际要移动的托盘或 IMEI 清单，不能按容器编号推算数量。

提交前显示实际箱数、托盘数和手机数，并要求确认目标门店。可选择：容器随货转移、仅手机转移、托盘随货但箱子留在原地。这样可以覆盖整箱配送和拆分配送。

### 5.7 门店收货

门店扫描配送单、箱、托盘或手机进行收货确认。系统将实收结果与出库快照比较，生成短收、多收、错货、损坏和 IMEI 不符差异单。门店不能通过手工改库存掩盖差异。

### 5.8 门店之间调拨

串货统一建模为门店调拨。发出方可以按手机、托盘或箱子创建调拨单；接收方逐台或按容器确认。发出后手机进入调拨中，接收确认后才进入目标门店库存。未确认调拨要显示超期提醒。

### 5.9 销售

销售支持单台、多台、整托盘和整箱操作，并区分零售和批发。系统始终将销售对象展开为 IMEI 明细，保存客户、价格、销售人员、门店、付款状态和凭证。整托盘/整箱只是一次选择全部当前内容；若只销售其中一部分，必须以实际手机或子托盘作为明细，剩余内容仍留在原容器。

整箱或整托盘销售时，箱子/托盘是操作入口，不代表数据库只保存一个汇总数字。

### 5.10 销售退回和维修

退回支持单台、多台、托盘或箱子。系统必须根据实际退回的 IMEI 建立退回明细，状态先进入销售退回待检测。按箱或托盘发起退回时也必须保存展开后的 IMEI 快照；容器中只退回一部分时，未退回手机不能被一并移动或改变状态。

维修链路：

```text
销售退回待检测 → 待送修 → 维修中 → 维修完成待验收
→ 可再次销售 / 冻结 / 报损
```

退回手机可整批运送到加纳管理处，但收货、维修和重新入库仍必须落实到每台 IMEI。

## 6. PWA 和手机浏览器体验

### 6.1 使用方式

系统采用响应式 Vue 前端。员工首次通过手机浏览器打开系统后，可选择“添加到主屏幕/安装应用”。安装后拥有独立图标、全屏或近似全屏启动、独立缓存和类似 App 的底部导航体验，不需要安装原生 App。

### 6.2 手机端设计原则

- 首页只展示当前角色可用的工作入口。
- 扫码页面占据主要空间，按钮大、对比度高，适合单手操作。
- 支持连续扫码，不必每扫一台重新点击。
- 成功时声音、震动、绿色提示；失败时说明具体原因。
- 关键提交动作需要二次确认，普通连续扫描不增加多余弹窗。
- 弱网时将扫描结果保存在本地待上传队列，并明确显示“待同步”；服务端确认前不能显示为最终完成。
- 手机端优先处理现场任务，复杂报表和权限配置放在桌面端后台。
- 组织和地点不要求员工手工输入数字编号；登录后由 `GET /auth/work-locations` 返回启用地点基础信息，任务页面按当前任务权限过滤来源地点，选择地点后自动带出组织。目的地点只显示启用地点基础信息，不因此扩大库存查看范围，业务接口仍执行服务端校验。

### 6.3 摄像头功能

优先采用条形码/二维码扫描；拍照用于验收、损坏、封条、维修和凭证留证。OCR 可以作为条码损坏时的辅助输入，但不能替代条码和 IMEI 唯一校验。

浏览器摄像头需要 HTTPS 和用户授权。系统应提供摄像头不可用时的手工输入入口，并兼容 Android Chrome、iPhone Safari 等主流浏览器。

## 7. 角色、权限和互动边界

权限采用 RBAC（角色权限）+ 数据范围 + 单据状态控制三层模型：

1. 功能权限：能否进入某功能；
2. 数据范围：能看哪些国家、组织、仓库、门店和字段；
3. 状态权限：单据处于什么状态时，谁能创建、提交、审核、取消或关闭。

### 7.1 角色定义

| 角色 | 主要范围 | 关键权限 | 明确限制 |
|---|---|---|---|
| 超级管理员 | 全系统 | 用户、角色、基础资料、参数、审计和故障处理 | 不应通过后台直接改库存，应使用纠正单 |
| 公司运营管理员 | 全业务组织 | 查看全链路、配置业务规则、审核异常、查看报表 | 不能绕过审计删除流水 |
| 深圳采购员 | 深圳采购组织 | 建采购批次、采购入库、维护采购信息 | 不能确认加纳收货、不能改已审核采购单 |
| 深圳仓库员 | 深圳仓库 | 装托盘、拆托盘、装箱、拆箱、盘点、仓库移位 | 不能修改采购价格和门店销售数据 |
| 深圳发运员 | 深圳发运 | 创建发运单、装运、封箱、上传物流资料 | 发运后取消需主管审核 |
| 加纳接收员 | 加纳管理处接收区 | 到货登记、拆箱、逐台验收、差异登记 | 不能直接将异常手机变为可售库存 |
| 加纳仓库员 | 加纳管理处库存 | 重组容器、仓库移位、按箱/托盘/手机向门店出库、盘点 | 不能确认销售、不能改维修结论 |
| 门店主管 | 本门店 | 收货、调拨审核、销售审核、退回和门店盘点 | 不能查看其他门店完整库存和成本 |
| 门店店员 | 本门店 | 扫码销售、收货执行、发起调拨、销售退回 | 不能删除销售、不能批准自己的异常 |
| 维修人员 | 加纳维修区 | 接收送修、记录检测/维修/配件、提交维修结果 | 不能修改原销售单和采购资料 |
| 财务/报表人员 | 授权组织 | 查看采购、销售、库存数量和金额报表 | 默认不能执行库存操作 |
| 审计/只读人员 | 授权组织 | 查看时间线、差异、操作日志和附件 | 不得新增或修改业务单据 |
| 系统运维人员 | 技术配置范围 | 查看系统运行状态、任务和错误日志 | 不应查看不必要的价格和客户隐私 |

### 7.2 关键互动规则

- 制单人与审核人可配置为不同人员，涉及金额、差异或异常时强制分离。
- 发出方只能确认“发出”，接收方只能确认“收到”；接收差异自动进入异常处理。
- 门店店员可以发起销售退回，但门店主管或管理处人员确认收货后才进入维修流程。
- 维修人员提交维修完成，管理处验收员确认是否恢复可售。
- 盘点人员可以提交盘点结果，但库存调整必须由主管审核并生成库存纠正单。
- 任何已确认单据不允许物理删除；撤销、作废和更正都必须保留原因、人员和时间。
- 用户只能操作当前所属组织和被授权地点的库存，临时跨组织任务通过授权委托实现并记录有效期。

## 8. 登录、账号和安全

登录支持两种方式：

1. 手机号或用户名 + 密码；
2. 手机号 + 短信验证码。

短信服务接口先抽象为 `SmsProvider`，当前实现可以是开发环境模拟器或空实现，保留发送验证码、校验验证码、频率限制和失败返回结构，待运营商文档确定后替换适配器，不改业务层。用户账号同时保留手机号和可选用户名：普通员工可用手机号登录，超级管理员等无手机号账号可用用户名登录。

密码必须使用带随机盐的不可逆哈希保存；当前后端基础层使用 Python 标准库 scrypt，避免依赖在 Python 3.13 下的 bcrypt 兼容问题。验证码只能短期有效、单次使用，并限制手机号、IP、设备和时间窗口的发送频率。登录后使用短期 Access Token 与可撤销 Refresh Token，重要操作可要求重新验证密码或验证码。

建议记录登录日志、设备信息、异常 IP、连续失败次数和账号锁定状态。个人手机丢失时，管理员可以撤销该设备的会话。

## 9. 数据与审计规则

核心数据表建议包括：

```text
users / roles / permissions / user_scopes
phone_devices
trays / boxes
phone_tray_relations
tray_box_relations
locations / organizations
purchase_orders / purchase_items
shipments / shipment_items
receiving_orders / receiving_items
transfer_orders / transfer_items
sales_orders / sales_items
return_orders / return_items
repair_orders / repair_items
stocktake_orders / stocktake_items
inventory_transactions
operation_audits
attachments
```

`phone_tray_relations` 和 `tray_box_relations` 保存开始时间、结束时间和触发单据。当前关系使用未结束记录或当前字段查询，历史关系不可覆盖。

每次库存或容器变化必须产生库存流水，至少记录：IMEI、原状态、目标状态、原地点、目标地点、原容器、目标容器、业务单号、操作人、时间、设备和备注。

所有会改变库存或建立业务单据的接口支持 `X-Idempotency-Key`。同一用户、同一业务动作和同一幂等键重复提交时，服务端返回第一次成功响应，不重新创建单据或重复变更库存；幂等键被不同用户或不同动作复用时拒绝请求。手机端一次现场任务生成一个操作键，断网草稿重试时继续使用原键。

容器级业务单据必须保存提交时的手机明细快照，不能在事后根据当前箱内内容重新计算历史单据。

## 10. 查询、盘点和异常

IMEI 查询应直接返回：当前状态、国家、组织、地点、箱号、托盘号、是否已售、最近业务和完整时间线。

还应支持按箱、托盘、发运单、采购批次、门店、机型和状态反向查询。

盘点支持扫描单台、多台、托盘或箱子。系统比较账面与实扫结果，输出正常、缺失、多出、位置错误和状态异常。容器扫码可以快速核对，但容器被拆分或重组后，必须以 IMEI 扫描结果为准。

盘点单提交后，缺失和多出差异不能由盘点人员直接改库存。拥有 `stocktake:adjust` 权限的主管处理差异：缺失可确认并将手机置为“冻结待核查”，多出必须指定合法目标库存状态和盘点地点，或选择忽略；每条处理意见写入盘点调整记录和库存流水。全部差异处理完成后盘点单才关闭。

## 11. 技术架构建议

后端：Python 3.x、FastAPI、Uvicorn、SQLAlchemy 2.x、Pydantic、Alembic、MySQL 8.x；必要时使用 Redis 处理验证码、会话、幂等键和异步任务。

前端：Vue 3.5、Vite、TypeScript、Pinia、响应式 UI 组件、PWA Service Worker。扫码可优先使用浏览器 BarcodeDetector API，并以 ZXing 等方案兼容不支持的浏览器。

接口按业务单据组织，而不是只提供任意修改库存的接口。例如：

```text
POST /purchase-receipts
POST /trays/{id}/add-phones
POST /boxes/{id}/add-trays
POST /shipments/{id}/dispatch
POST /receipts/{id}/unpack
POST /receipts/{id}/accept
POST /transfers/{id}/ship
POST /transfers/{id}/receive
POST /sales/{id}/confirm
POST /returns/{id}/submit
POST /repairs/{id}/complete
POST /stocktakes/{id}/submit
```

所有写接口都应支持幂等键，避免网络重复提交造成重复出库或重复销售。

## 12. 分阶段开发计划

### 第一阶段：可用闭环

用户登录、组织和权限、手机档案、IMEI 扫码、采购入库、托盘/箱子、深圳发运、加纳接收验收、管理处出库、门店收货、IMEI 查询和基础盘点。

### 第二阶段：门店经营闭环

门店调拨、批发/零售销售、销售退回、维修、维修后验收、销售和库存报表、差异审核。

### 第三阶段：现场效率和治理

离线扫描队列、批量打印标签、照片压缩和对象存储、短信运营商接入、设备会话管理、消息提醒、成本/售价权限细化和审计报表。

## 13. 开发验收标准

- 任意一台手机输入 IMEI，都能看到当前状态、当前位置和完整流转历史。
- 原箱拆开后可以建立新的托盘和箱子关系，且旧关系历史仍可查询。
- 任意箱子、托盘或手机都可以发起出库、调拨、销售、退回和送修。
- 容器数量不固定时，系统按实际展开的 IMEI 数量处理，不使用固定容量假设。
- 已确认业务不能被静默修改或删除。
- 不同角色只能访问授权组织、地点和字段。
- 手机浏览器可以扫码、拍照、连续操作，并可安装到桌面作为 PWA 使用。
- 短信登录接口存在清晰适配层，未接入运营商时不会影响密码登录和开发测试。
- 断网或重复提交不会产生重复库存流水；待同步数据有明确状态。

## 14. 后台权限落地规则

权限不能只停留在菜单隐藏。后端每次请求都必须重新校验用户身份、角色、数据范围、单据状态和对象当前归属，前端按钮隐藏只用于改善体验，不能作为安全措施。

### 14.1 权限维度

每个权限由以下维度组成：

```text
资源：手机/托盘/箱子/采购单/发运单/验收单/调拨单/销售单/退回单/维修单/盘点单
动作：查看/创建/编辑草稿/扫描加入/提交/审核/发出/接收/拆分/撤销/导出
数据范围：全部/国家/组织/仓库/门店/本人创建
字段范围：全部/隐藏采购价/隐藏销售价/隐藏客户资料
```

例如“门店店员”的权限应表达为：

```text
销售单：查看本店、创建、扫描加入、提交
销售单：不能审核、不能删除、不能修改已确认单
手机：只能查看本店待售手机的必要字段
采购价：不可见
```

安全默认值为“无范围即拒绝”：功能权限本身不等于全量数据权限。只有为该权限明确配置 `ALL`、国家、组织、地点或本人范围后，后端才允许访问对应资源。

当前已落地后台最小闭环：组织、地点、角色、权限和用户的查询接口，以及组织、地点、角色和用户的创建、基础更新和启停接口；PWA 管理页提供用户、组织、地点、角色和审计入口。用户支持修改显示名、密码、启停状态、角色和数据范围，组织和地点停用不会删除历史单据。后台管理接口要求对应管理权限同时具备 `ALL` 数据范围；创建或更新角色/用户时，不允许授予当前管理员自身没有的权限，用户范围也必须由管理员明确提交。库存和单据查询已按权限隐藏金额字段；`GET /admin/audits` 提供全局审计查询接口。完整审计报表、字段级更细粒度脱敏和完整桌面端配置页面属于后续工作。

### 14.2 单据状态权限

所有单据统一使用状态机，建议状态包括：草稿、待审核、已审核、执行中、待接收、已完成、部分差异、已关闭、已取消。

不同角色对同一单据的动作不同：

| 单据 | 制单/执行 | 审核 | 接收/验收 | 差异关闭 |
|---|---|---|---|---|
| 采购入库 | 深圳采购员 | 深圳采购主管/运营管理员 | 不适用 | 运营管理员 |
| 装托盘/装箱 | 深圳仓库员 | 仓库主管，可配置为自动审核 | 不适用 | 仓库主管 |
| 深圳发运 | 深圳发运员 | 深圳发运主管/运营管理员 | 加纳接收员确认到货 | 运营管理员 |
| 加纳验收 | 加纳接收员 | 加纳接收主管/运营管理员 | 加纳接收员逐台验收 | 运营管理员 |
| 管理处出库 | 加纳仓库员 | 加纳仓库主管 | 门店人员 | 运营管理员 |
| 门店收货 | 门店店员 | 门店主管 | 门店店员/主管 | 管理处主管 |
| 门店调拨 | 发出门店店员 | 发出门店主管 | 接收门店 | 运营管理员 |
| 销售 | 门店店员 | 门店主管，按金额可强制 | 不适用 | 运营管理员/财务授权 |
| 销售退回 | 门店店员 | 门店主管 | 加纳管理处接收员 | 维修/运营主管 |
| 维修 | 维修人员 | 管理处维修主管 | 管理处验收员 | 运营管理员 |
| 盘点 | 盘点人员 | 组织主管 | 不适用 | 运营管理员 |

系统应提供“主管”角色的独立权限，而不是让普通操作员兼任所有动作。小团队可以由同一个实际人员承担多个角色，但账号权限仍按角色叠加，并对自制自审设置风险提示或禁止规则。

### 14.3 高风险操作

以下操作必须要求原因，并写入审计日志；涉及库存数量或金额时建议二次认证：

- 取消或关闭已提交单据；
- 把冻结、异常或维修手机恢复为可售；
- 库存纠正、盘盈盘亏确认；
- 修改 IMEI、采购价、销售价或客户资料；
- 将手机从一个组织强制转到另一个组织；
- 解锁已封箱容器；
- 撤销已发运、已收货或已销售记录。

## 15. 各角色的实际工作界面

### 15.1 深圳采购员

首页显示“采购入库、待补资料、我的草稿、异常 IMEI”。采购入库页以连续扫码为主，补录信息按必填和可选分组，避免一次显示全部字段。

### 15.2 深圳仓库员

首页显示“装托盘、装箱、拆托盘、拆箱、仓库移位、盘点”。扫码一个托盘或箱子后，页面显示当前包含的手机数量、容器数量和最近操作，不显示无关价格信息。

### 15.3 深圳发运员

首页显示“待装运发运单、封箱确认、物流资料、已发运查询”。发运确认页必须同时显示箱数、托盘数和 IMEI 总数，并提供封条照片上传。

### 15.4 加纳接收员

首页显示“待到货、待拆箱、待验收、异常待处理”。验收页支持边拆边扫，扫到异常 IMEI 时可以拍照并转入冻结，不阻塞其他正常手机的验收。

### 15.5 加纳仓库员

首页显示“管理处库存、重组托盘/箱、门店配送、待出库、盘点”。拣货页必须按当前位置排序或分组，显示箱号、托盘号和实际数量，减少找货时间。

### 15.6 门店店员和主管

店员首页只显示“收货、销售、调拨、退回、查询本店库存”。主管额外显示待审核、差异处理、销售汇总和盘点确认。销售页默认扫码一台，支持继续添加手机或扫描整托盘/整箱。

### 15.7 维修人员

首页显示“待接收、维修中、待提交结果、已完成待验收”。维修人员只需处理 IMEI、故障、照片、维修项目和结果，不显示不必要的采购或其他门店数据。

### 15.8 管理、财务和审计人员

桌面端提供库存总览、流转时间线、差异、销售和维修报表。管理人员能钻取到 IMEI；财务默认按授权范围查看金额；审计人员只读并能看到单据快照、操作人、设备和时间。

## 16. 容器移动的交互细节

系统将“容器本身的去向”和“容器中手机的去向”分开确认。扫描箱子或托盘后，提交前明确显示处理方式。容器不是固定容量单位，页面必须显示本次实际展开的托盘数、手机数以及操作后剩余数：

```text
A. 容器及其中全部手机一起移动
B. 只移动手机，容器留在原地点
C. 手机和托盘一起移动，外层箱子留在原地点
D. 拆出部分手机/托盘，剩余内容留在原容器
```

选择 D 时，系统要求扫描或选择实际移出的对象，并在提交前显示：

```text
原箱：BOX-001，原手机 50 台
本次移出：手机 12 台，托盘 1 个
操作后剩余：手机 38 台，托盘数量按实际重算
```

若整箱销售或整箱退回，业务明细仍保存当时展开的 IMEI 清单。容器是否回收、随货、留在原地或报损，作为独立的容器处理结果保存。

## 17. PWA 实现与验收细节

前端需提供有效的 Web App Manifest，至少配置应用名称、短名称、图标、主题色、背景色、`standalone` 显示模式和启动路径；生产环境必须通过 HTTPS 提供服务。Service Worker 负责缓存应用壳、静态资源和安全的离线草稿，不缓存敏感业务响应到公共缓存。

首次打开时提示安装条件和“添加到主屏幕”方法。安装后页面应保持登录态，但设备丢失或管理员撤销会话后必须重新登录。不同手机屏幕尺寸下，扫码框、主要按钮和底部导航不得被刘海、浏览器工具栏或键盘遮挡。

PWA 的离线策略只允许保存未提交的扫码操作和表单草稿。每条待同步记录要有本地唯一 ID、创建时间、操作者、业务动作、完整表单快照、原幂等键和同步状态。重新联网后，单据中心可以逐条或批量重试；服务端按幂等键校验，已成功的请求返回原响应，业务状态冲突保留为“冲突”并显示原因，不自动覆盖或删除。

## 18. 设计假设与需要现场确认的事项

以下事项不阻塞总体设计，但开发前应由业务负责人确认并写入配置：

1. 双卡手机是否两个 IMEI 都必须扫描；
2. 箱子是否始终只装托盘，还是允许直接放手机；
3. 容器随货后是否需要回收跟踪；
4. 门店整箱/整托盘销售是否代表所有内容一次性售出；
5. 批发销售是否需要客户档案和信用额度；
6. 价格、成本和客户信息的可见范围；
7. 加纳现场的网络稳定性和是否必须第一版支持离线；
8. 是否需要中文、英文或中英双语界面；
9. 退回手机是否必须经过维修，还是可直接验收后重新销售；
10. 盘点差异的金额审批阈值和组织负责人。

这些配置应存入系统参数表，由授权管理员维护，而不是写死在前端代码中。

## 19. 开发顺序建议

第一步先实现领域模型和库存流水，包括手机、容器关系、地点、业务单据、状态机和权限校验；第二步实现管理资料和权限的最小后台闭环；第三步实现手机端 PWA 扫码闭环；第四步加入离线队列、照片和短信适配；最后根据真实操作试运行结果完善桌面端报表和配置体验。

开发每个业务流程时都应同时完成：正常路径、重复扫码、错误状态、权限不足、接收差异、网络中断和重复提交测试，避免只验证“顺利完成”的情况。

## 20. 当前实现进度

当前代码已经完成受权限保护的业务闭环试运行版本：

```text
手机号密码登录
→ 数据库加载用户角色/权限/数据范围
→ 采购入库并建立 IMEI 手机档案
→ 创建托盘并加入手机
→ 创建箱子并加入托盘
→ 查询手机当前托盘和箱子
```

对应接口为：

```text
POST /api/v1/auth/password
GET  /api/v1/auth/me
POST /api/v1/inventory/purchase-receipts
POST /api/v1/inventory/trays
POST /api/v1/inventory/boxes
GET  /api/v1/inventory/phones/{imei}
```

当前短信登录仍是运营商适配层占位；超级管理员可通过后端初始化命令幂等创建，生产上线前仍需接入短信运营商、完善离线冲突的有权限复核流程、组织/地点完整维护和后台报表配置页面。

跨国发运和加纳接收的第一版接口也已加入：

```text
POST /api/v1/shipments/dispatch
POST /api/v1/shipments/receiving/start
POST /api/v1/shipments/receiving/inspect
```

发运时支持按手机、托盘或箱子选择对象，并保存 IMEI 快照及来源容器；加纳开始接收时会按当前关系拆离已发运手机，只有验收通过的手机进入加纳管理处库存，异常手机进入冻结待核查。部分托盘发运时，未发运的手机仍保留原托盘和箱子关系。

验收接口支持在逐台验收通过时可选指定目标托盘和目标箱子。目标容器不存在时可以按编号创建，已存在时复用；指定箱子必须同时指定托盘。系统仍不记录托盘槽位，只记录手机—托盘和托盘—箱子的当前关系及历史关系，因此不同托盘、不同箱子的数量可以完全不一致。

管理处向门店配送的第一版接口也已加入：

```text
POST /api/v1/transfers/issue
POST /api/v1/transfers/receive
```

调拨/配送支持按手机、托盘或箱子发出。门店收货时提交实际收到的 IMEI 清单；若提交完成且存在短少，已收到手机进入门店库存，短少手机进入冻结待核查，单据标记为部分差异。整箱或整托盘随货时，容器当前位置同步到目标地点；只移动部分手机时，剩余手机和容器关系继续留在原状态。

销售和退回的第一版接口也已加入：

```text
POST /api/v1/sales
POST /api/v1/sales/{sales_no}/confirm
POST /api/v1/sales/{sales_no}/cancel
POST /api/v1/returns
POST /api/v1/returns/receive
```

店员创建销售单后手机先进入“销售待确认”，主管确认后才进入“已售出”，制单人不能确认自己的销售单。销售退回必须引用原销售单并提交具体 IMEI；管理处收到后手机进入“待送修”，随后由维修流程决定是否恢复可售。

维修第一版接口已加入：

```text
POST /api/v1/repairs
POST /api/v1/repairs/{repair_no}/accept
POST /api/v1/repairs/{repair_no}/complete
POST /api/v1/repairs/{repair_no}/review
```

维修人员先接收送修单，再填写每台手机的故障、诊断、维修项目、配件、费用和结果；管理处验收员独立复核并决定恢复可售、冻结或报损。维修人员不能验收自己完成的维修。

手机端 PWA 工作台已实现：登录后调用 `/auth/me` 获取权限和数据范围，只展示当前账号有权限的工作入口；支持密码登录、验证码登录入口、PWA 添加到桌面提示、在线/离线状态显示、摄像头连续扫码、手工输入降级、去重扫描列表和提交前确认。摄像头权限被拒绝或浏览器不支持时，不阻塞手工录入。采购入库、装托盘、装箱、发运、接收建单/验收、调拨发出/收货、销售制单/确认、退回发起/接收、维修四阶段、盘点和 IMEI 查询均已接入后端；单 IMEI 的验收和维修动作在多扫时逐条提交并汇总结果。

盘点差异审核接口为 `POST /api/v1/stocktakes/{stocktake_no}/adjust`。缺失、多出和忽略必须由具备 `stocktake:adjust` 的人员处理，库存纠正和审核意见均写入流水；库存变更接口支持 `X-Idempotency-Key`，PWA 离线草稿保存完整表单并可在单据中心重试。
